✅ FASE 3 — COMPLETATA (2026-08-10)

L'architettura di /sbin/init è stata completamente rifattorizzata in una struttura modulare pulita:
  init/
  ├── init.c       (PID 1 main entry point & supervisor loop)
  ├── init.h       (common declarations & shared data structures)
  ├── mount.c/h    (VFS & fstab mounting with LABEL=/UUID= resolution)
  ├── services.c/h (hostname, rc.sysinit, and rc.d service runner)
  ├── signals.c/h  (signal handlers & zombie child reaping)
  ├── tty.c/h      (TTY supervision & login spawning)
  └── shutdown.c   (system shutdown & reboot syscall engine)

Commit: refactor(init): modularize PID 1 init architecture

Questa secondo me è una ottima idea.

E la metterei abbastanza presto.

Architettura:

                   ▼

Deve occuparsi di:

Coldplug

/sys/class

NETLINK_KOBJECT_UEVENT

per eventi come:

add

/dev

Per esempio:

/dev/null
/dev/zero

È un componente molto importante per l'identità di KratosOS.

FASE 5 — Filesystem e mount system

Qui migliorerei parecchio quello che hai ora.

Il tuo:

/etc/fstab

deve diventare realmente utilizzabile.

Per esempio:

UUID=xxxx   /       ext4    defaults   0 1
UUID=yyyy   /boot   vfat    defaults   0 2
proc        /proc   proc    defaults   0 0
sysfs       /sys    sysfs   defaults   0 0

E init deve riuscire a:

/dev
/proc
/sys
/run
/tmp
/dev/pts
/dev/shm

senza dipendere da mount fatti manualmente dall'ambiente host.

FASE 6 — Account e login

FASE 7 — Package manager

Qui inizierei a costruire uno dei componenti più caratteristici di KratosOS.

Non farei subito qualcosa di enorme.

Creerei:

kratos-pkg

oppure:

kpm
Prima versione

Dovrebbe poter fare:

kpm install package
kpm remove package
kpm update
kpm search package
kpm info package
kpm list
Database

Per esempio:

/var/lib/kratos/pkg/

con:

installed/
available/
database/

Ogni pacchetto potrebbe contenere:

package/
├── metadata
├── files/
├── scripts/
└── manifest

Metadata:

name=bash
version=5.x
arch=x86_64
depends=glibc
Ma soprattutto

Devi decidere che formato di pacchetto vuoi.

Io eviterei di copiare semplicemente .deb o .rpm.

Potresti avere qualcosa come:

bash-5.x-x86_64.kpkg

e un archivio interno:

metadata
manifest
payload.tar.zst

Questo renderebbe KratosOS realmente indipendente dal packaging di Debian/Arch.

FASE 12 — Servizi

Il tuo:

/etc/rc.d/

può diventare il sistema di servizi di KratosOS.

Per esempio:

/etc/rc.d/
├── devd
├── networking
├── syslog
├── sshd
└── cron

Potresti definire un formato estremamente semplice:

start()
stop()
restart()
status()

e far gestire tutto a init.

Quindi:

service networking start
service networking status

oppure un tuo comando:

kratosctl service networking start
FASE 13 — kratosctl

A questo punto inizierei a creare un comando centrale:

kratosctl

che gestisce:

kratosctl reboot
kratosctl poweroff
kratosctl hostname
kratosctl users
kratosctl package

Non deve diventare un "systemd clone".

Deve essere semplicemente l'interfaccia amministrativa di KratosOS.

Un'importante distinzione

A questo punto eviterei di aggiungere funzionalità semplicemente perché "sarebbe bello averle".

Per ogni componente chiediti:

È necessario per trasformare il prototipo attuale in un sistema utilizzabile?

Se sì → roadmap.

Se no → backlog.

Per esempio:

Componente	Priorità
Boot EFI	🔴 Critica
init/PID 1	🔴 Critica
devd	🔴 Critica
mount/VFS	🔴 Critica
login	🔴 Critica
package manager	🟠 Alta
repository	🟠 Alta
networking	🟠 Alta
coreutils	🟠 Alta
service manager	🟡 Media
installer	🟡 Media
GUI	🟢 Dopo
desktop proprietario	🟢 Molto dopo

Il prossimo obiettivo concreto, quindi, non è il package manager: è chiudere definitivamente la catena disk image → EFI → GRUB → kernel → init → login, provarla in QEMU in modo pulito e poi fare il primo boot su hardware reale. Dopo quello, kratos-devd è probabilmente il componente migliore da affrontare.
